# Neurons · .github

refreshed 2026-10-09 · e52a377a71d9

- Two workflows now, not one: `ci.yml` (lint/breaking/gen-is-current/build/tsc, plus npm publish on push) and the new `security.yml` (gitleaks secret scan). They are independent — `security.yml` is not a dependency of `ci.yml`'s `check` job and does not gate the breaking check.
- `ci.yml`: `check` (PRs, main, `v*` tags) and `publish-ts` (pushes only, `needs: check`). CI calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make` — a change to the `Makefile` alone is not exercised by CI, so keep the two in step by hand.
- The breaking check is still the point of `ci.yml`: `.github/workflows/ci.yml:31` says a wire break here "would be a production incident in web/mobile/agent-runner, so it is caught at the source". It runs only `if: github.event_name == 'pull_request'`, and needs `git fetch --no-tags origin main:main` first because `actions/checkout` leaves a PR on a detached merge commit with no local `main` ref — the same applies locally on a fresh clone.
- `security.yml` is a deliberate duplication, not a design choice: its header comment explains that `workflows/.github/workflows/secret-scan.yml` is a reusable workflow in a *private* repo, and GitHub refuses a reusable workflow call from a private repo into this *public* one before any job is even scheduled — a nought-second failure with no log. So the rules are reproduced here by hand; the comment calls out exactly which ones must not drift if the real file changes: gitleaks pinned as a release binary (not the Action, which asks for a licence key), findings redacted in a public repo's readable logs, the scanner always exits 0 so the report step decides (a crash must not read as a clean scan), and no report at all is itself a failure.
- `security.yml` triggers on PR, push to main, a weekly `17 6 * * 1` full-history scan, and `workflow_dispatch`. `HISTORY` (`github.event_name == 'schedule'`) switches `fetch-depth` (0 for history, 1 otherwise) and the gitleaks invocation (`git .` vs `dir .`) — a credential committed and reverted is still a leak in a public repo, which is why the scheduled run walks all of history.
- `security.yml`'s `report` step is the actual gate: it fails if `gitleaks.sarif` is missing (`always()` + explicit file check — "an unknown result is a failure, never a pass") and again if the SARIF has findings; a false positive is meant to be silenced with a dated `.gitleaksignore` entry, never by weakening this check.
- `actions/checkout@v4` is pinned to `fetch-depth: 0` in `ci.yml` purely so the breaking check has history; shallowing it breaks the comparison, not the build.
- The staleness gate in `ci.yml` is `buf generate` followed by `git diff --exit-code --stat gen/`, failing with `::error::gen/ is stale. Run 'make gen' and commit the result.` Regenerating with a different buf or plugin version than the pins in `buf.gen.yaml` will trip it.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`, so bumping Go means editing `go.mod`. The TypeScript check is `npm install --no-audit --no-fund && npm run build` in `gen/ts` on node 24 — a tsc compile of the generated sources, no tests.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes `${GITHUB_REF_NAME#v}` under dist-tag `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`. PRs never publish (`github.event_name == 'push'` gate). Publishing goes to GitHub Packages, authenticated with `NODE_AUTH_TOKEN: ${{ github.token }}` — no external npm credential needed.
- Permissions are least-privilege in both files: `contents: read` at the top of each; only `ci.yml`'s `publish-ts` adds `packages: write`. `ci.yml` has `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true`; `security.yml` has no concurrency group, so a scheduled scan and a push scan can run side by side.
