- Two workflows now: `ci.yml` (lint, breaking, gen-freshness, Go build, tsc build, npm publish) and `security.yml` (secret scanning), added this cycle. `ci.yml` is unchanged from the prior refresh; everything below on `security.yml` is new.
- `ci.yml` has two jobs: `check` (PRs, main, `v*` tags) and `publish-ts` (pushes only, `needs: check`). CI calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make` — a change to the `Makefile` alone is not exercised by CI, the two must be kept in step by hand.
- The breaking check is the point of `ci.yml`: `.github/workflows/ci.yml:31` says a wire break here "would be a production incident in web/mobile/agent-runner, so it is caught at the source". It runs only `if: github.event_name == 'pull_request'`, and needs `actions/checkout@v4` with `fetch-depth: 0` plus `git fetch --no-tags origin main:main` first — `actions/checkout` leaves a PR on a detached merge commit with no local `main` ref.
- The staleness gate is `buf generate` followed by `git diff --exit-code --stat gen/`, failing with `::error::gen/ is stale. Run 'make gen' and commit the result.` Regenerating with a different buf or plugin version than the pins in `buf.gen.yaml` will trip it.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes `${GITHUB_REF_NAME#v}` under dist-tag `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`, authenticated with `NODE_AUTH_TOKEN: ${{ github.token }}` against GitHub Packages.
- `security.yml` is brand new and has thrashed hard in the last three commits (34e2dd6, 6b1c4b7, 572da95) in one evening — read the current file, not the history, before trusting what it runs.
- It started as two jobs appended straight into `ci.yml` (secrets + deps via reusable workflows), which GitHub rejected before scheduling any job at all ("workflow-file error", zero jobs run) — that is why it is its own file and not a job in `ci.yml`.
- It was then split into its own `security.yml` with both `secrets` (calling `tactical-agent-neural-knowledge/workflows/.github/workflows/secret-scan.yml@main`, plus a Monday 06:17 UTC `schedule` trigger that walks full git history) and `deps` (calling `.../deps-scan.yml@main`) — but *that* two-job version also failed with the same workflow-file error and zero scheduled jobs, in every repo that adopted it except infra's (which only calls iac + secrets, never deps).
- Current state (572da95) is narrowed to one job only: `secrets` calling `secret-scan.yml@main`, no `with:` inputs, no `schedule` trigger. The `deps` job, the history-walk schedule, and the explanatory header comment were all removed to isolate which reusable-workflow call GitHub was rejecting — this is a diagnostic rollback, not a final design; expect `deps` (and probably the schedule) to come back once the call that trips GitHub is identified. Do not assume dependency scanning is covered by anything in this repo today.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`, so bumping Go means editing `go.mod`. Permissions are least-privilege: `contents: read` at the top of both workflow files, `publish-ts` alone adds `packages: write`.
- `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true` on `ci.yml` only — `security.yml` has no concurrency group, so overlapping secret-scan runs on the same ref are not cancelled.
