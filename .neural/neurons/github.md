# Neurons · .github

refreshed 2026-10-10 · e52a377a71d9

- Two workflows now, not one: `ci.yml` (lint/breaking/gen/build/tsc, plus npm publish) and the new `security.yml` (secret scanning). They are independent — nothing in `security.yml` gates `ci.yml` or vice versa.
- `ci.yml` has two jobs: `check` (PRs, main, `v*` tags) and `publish-ts` (pushes only, `needs: check`). CI calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make` — a change to the `Makefile` alone is not exercised by CI, the two must be kept in step by hand.
- The breaking check is the point of `ci.yml`: `.github/workflows/ci.yml:31` says a wire break here "would be a production incident in web/mobile/agent-runner, so it is caught at the source." It runs only `if: github.event_name == 'pull_request'`.
- Trap: `actions/checkout` leaves a PR on a detached merge commit with no local `main`, so the step must `git fetch --no-tags origin main:main` before `buf breaking --against ".git#branch=main"` can read it — same requirement locally on a fresh clone. `actions/checkout@v4` is pinned to `fetch-depth: 0` purely for this.
- The staleness gate is `buf generate` followed by `git diff --exit-code --stat gen/`, failing with `::error::gen/ is stale. Run 'make gen' and commit the result.` A buf/plugin version mismatch against `buf.gen.yaml`'s pins will trip it.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`. `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes under `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`, authenticated with `NODE_AUTH_TOKEN: ${{ github.token }}` against GitHub Packages. `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true` — a second push to the same ref kills a half-finished publish.
- `security.yml` is a secret scan (gitleaks) **inlined rather than called as a reusable workflow**, and the file's own header comment (`security.yml:1-18`) explains why: this repo is public, the org's shared `workflows` repo is private, and GitHub refuses a reusable workflow from a private repo into a public caller before any job is even scheduled — so the call used to fail with a zero-second run and no log, red on every push since the gate was adopted. The rules of `workflows/.github/workflows/secret-scan.yml` are duplicated here by hand instead; that duplication is the ongoing price of this repo being public, and the two must be kept in sync by hand same as `ci.yml`/`Makefile`.
- `security.yml` triggers: PR and push-to-main do a tree scan (`gitleaks dir .`, `fetch-depth: 1`); a Monday 06:17 UTC cron does a full-history scan (`gitleaks git .`, `fetch-depth: 0`) because a committed-then-reverted credential is still leaked. `workflow_dispatch` is also wired for an ad hoc run.
- `security.yml` always runs gitleaks with `--exit-code 0` and lets the separate `report` step decide pass/fail from the SARIF file — a scanner crash must never read as a clean scan. No SARIF file at all is itself a hard failure (`::error::gitleaks produced no report — an unknown result is a failure, never a pass`), not a silent pass.
- `security.yml` redacts findings (`--redact`) because the run log and step summary are readable by anyone who can read this public repo; a false positive is silenced with a dated `.gitleaksignore` entry, never by weakening or dropping the check.
- Permissions are least-privilege on both workflows: each declares `contents: read` at the top; only `ci.yml`'s `publish-ts` adds `packages: write`.

## Verified
