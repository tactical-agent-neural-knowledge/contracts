# Neurons · .github

refreshed 2026-10-08 · a887d51f4d82

- Two workflows now: `ci.yml` (unchanged since the last refresh) and the new `security.yml`, added for the secret scan.
- `ci.yml` has two jobs: `check` (PRs, main, `v*` tags) and `publish-ts` (pushes only, `needs: check`). It calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make` — a change to the `Makefile` alone is not exercised by CI, the two must be kept in step by hand.
- The breaking check is the point of `ci.yml`: a wire break here "would be a production incident in web/mobile/agent-runner, so it is caught at the source". It runs only `if: github.event_name == 'pull_request'`, and needs `git fetch --no-tags origin main:main` first because `actions/checkout` leaves a PR on a detached merge commit with no local `main` — same trap on a fresh clone locally.
- `security.yml` runs gitleaks, and its header comment explains why it is a 95-line inline workflow instead of a one-line call to a reusable one: this repo is **public**, the org's shared `workflows` repo is **private**, and GitHub refuses a reusable workflow from a private repo to a public caller before any job is even scheduled. The gate had been failing silently (a nought-second run, no job, no log) on every push since it was adopted — "red forever, scanning nothing, and indistinguishable from a gate that is working." Any future divergence from `workflows/.github/workflows/secret-scan.yml` has to be reconciled by hand; there is no shared source to diff against.
- `security.yml` triggers on `pull_request`, `push` to main, a weekly `schedule` (Monday 06:17 UTC), and `workflow_dispatch`. Only the scheduled run does a full-history scan (`fetch-depth: 0`, `gitleaks git .`); PR/push runs scan the working tree only (`fetch-depth: 1`, `gitleaks dir .`) — "a credential committed and reverted is still a credential that leaked," so history is swept weekly rather than never.
- `security.yml` always runs gitleaks with `--exit-code 0` and lets the separate `report` step decide pass/fail by reading `gitleaks.sarif` with `jq`: a scanner crash can't accidentally read as a clean scan, and "no report at all" (`if [ ! -f gitleaks.sarif ]`) is treated as a hard failure, never a silent pass.
- gitleaks is pinned (`VERSION: "8.30.1"`) and fetched as a release binary from GitHub directly, not via a Marketplace Action — the Action's own setup asks organisations for a licence key, which this repo avoids by calling the binary itself.
- Findings are always `--redact`ed in `security.yml`: the run log and the `GITHUB_STEP_SUMMARY` are world-readable on a public repo, so raw secret values never reach either. A false positive is silenced with a dated `.gitleaksignore` entry, "never by dropping this check."
- The staleness gate in `ci.yml` is `buf generate` followed by `git diff --exit-code --stat gen/`, failing with `::error::gen/ is stale. Run 'make gen' and commit the result.` Regenerating with a different buf or plugin version than the pins in `buf.gen.yaml` will trip it.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`, so bumping Go means editing `go.mod`.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes `${GITHUB_REF_NAME#v}` under dist-tag `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`. PRs never publish, gated on `github.event_name == 'push'`.
- Permissions are least-privilege and deliberate across both workflows: `contents: read` at the top of each, `publish-ts` alone adds `packages: write`. `ci.yml` has `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true`; `security.yml` has no concurrency group, so overlapping scheduled/PR runs are not cancelled.
