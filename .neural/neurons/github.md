# Neurons · .github

refreshed 2026-10-14 · 65c4439b3e7d

- Two workflows now: `ci.yml` (unchanged this refresh) and the new `security.yml`.
- `.github/workflows/ci.yml` has two jobs: `check` (PRs, main, `v*` tags) and `publish-ts` (pushes only, `needs: check`). CI calls `buf` directly via `bufbuild/buf-setup-action@v1`, never `make` — a change to the `Makefile` alone is not exercised by CI, the two must be kept in step by hand.
- `ci.yml`'s breaking check runs only `if: github.event_name == 'pull_request'` and needs `git fetch --no-tags origin main:main` first, because `actions/checkout` leaves a PR on a detached merge commit with no local `main` — `fetch-depth: 0` on the checkout exists solely for this. The same fetch is needed locally on a fresh clone before `buf breaking --against '.git#branch=main'` will work.
- `ci.yml`'s staleness gate is `buf generate` then `git diff --exit-code --stat gen/`, failing `::error::gen/ is stale. Run 'make gen' and commit the result.` — a buf/plugin version drift from the pins in `buf.gen.yaml` trips it even with no proto change.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under dist-tag `canary`, a `v*` tag publishes `${GITHUB_REF_NAME#v}` under `latest`. PRs never publish (`if: github.event_name == 'push'`). Merging to main is already a publish.
- `.github/workflows/security.yml` is new and is the gitleaks secret scan — and it exists as a 95-line inline duplicate of `workflows/.github/workflows/secret-scan.yml` (a different, private repo) rather than a call to it, because **GitHub refuses a reusable workflow from a private repo to a public caller before any job is scheduled**: that produced a nought-second failure with no job and no log, and it had been silently red on every push since the gate was adopted — "indistinguishable from a gate that is working until somebody opens it" (the workflow's own header comment). If a reusable-workflow call to a private repo ever needs adding back here, check whether this repo is still public first.
- `security.yml` fetches gitleaks as a pinned release binary (`VERSION: "8.30.1"`) rather than using the gitleaks Action, because the Action asks organizations for a licence key this repo doesn't have.
- `security.yml` scans the working tree (`gitleaks dir`, `fetch-depth: 1`) on every PR and push, and the full git history (`gitleaks git .`, `fetch-depth: 0`) only on the Monday 06:17 UTC cron — a credential committed and reverted is still leaked in a public repo, so the expensive full-history scan is scheduled rather than run on every push.
- `security.yml`'s scan step always exits 0 (`--exit-code 0`); a separate `report` step (`if: always()`) parses the SARIF and decides pass/fail. If the SARIF file is missing entirely, that is treated as a failure, never a pass — a crashed scanner must not look like a clean one. Findings are redacted in the summary and the log because this repo is public and readable by anyone.
- A false positive in `security.yml` is silenced with a dated entry in `.gitleaksignore`, never by dropping the check (per the workflow's own comment) — there is no `.gitleaksignore` in the repo as of this refresh.
- Permissions stay least-privilege: `ci.yml` and `security.yml` both declare `contents: read` at the top; only `publish-ts` adds `packages: write`. `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true` on `ci.yml` means a second push to the same ref kills the first run, including a half-finished publish.
