- Two workflows now, not one: `ci.yml` (lint, breaking, gen-is-current, go build, tsc, npm publish) and the new `security.yml` (secret scanning). They are independent — `security` is never a dependency of `check` or `publish-ts` and does not gate a merge by itself.
- `ci.yml` is unchanged this refresh: `check` job (PRs, main, `v*` tags) runs `buf lint`, `buf breaking` (PR-only), the `buf generate` + `git diff --exit-code --stat gen/` staleness gate, `go build ./...`, then `npm install && npm run build` in `gen/ts`; `publish-ts` (push-only, `needs: check`) publishes to GitHub Packages.
- CI calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make`. A change to the `Makefile` alone is therefore not exercised by CI — the two must be kept in step by hand.
- Breaking-check trap, unchanged: `actions/checkout` leaves a PR on a detached merge commit with no local `main`, so the step must `git fetch --no-tags origin main:main` before `buf breaking --against ".git#branch=main"` can read it. The same applies locally on a fresh clone. `fetch-depth: 0` on `actions/checkout@v4` exists purely so this history is there.
- `security.yml` is a single job (`secrets`) that runs gitleaks on: every PR, every push to `main`, a weekly cron (`17 6 * * 1`, full git history), and `workflow_dispatch`. It is a *tree* scan (`gitleaks dir .`, `fetch-depth: 1`) on PR/push and a *history* scan (`gitleaks git .`, `fetch-depth: 0`) only on the weekly cron — `env.HISTORY` is `github.event_name == 'schedule'`.
- `security.yml:3-18` is a long comment explaining why the file exists instead of calling a reusable workflow: this repo is **public**, a shared workflow lives in a **private** `workflows` repo, and GitHub refuses a private-repo reusable workflow for a public caller before any job is even scheduled — the prior setup failed silently (a nought-second run, no job, no log) on every push since adopted. The rules are reproduced here by hand and must not drift: gitleaks pinned as a release binary (not the Action, which wants an org licence key), findings redacted (the log is public), scanner always exits 0 so the `report` step is the sole arbiter, and no report at all is treated as a failure, never a pass (`gitleaks.sarif` missing → `exit 1`).
- A real finding fails the build (`::error::gitleaks found $n secret(s)`); a false positive is silenced only with a dated entry in `.gitleaksignore` (not present in the repo yet — none has been needed), never by dropping the check. `security.yml` only declares `permissions: contents: read` — no `packages:` or `pull-requests:` scope, so it cannot itself write anything.
- The gitleaks SARIF is uploaded as a build artifact (`gitleaks-sarif`, 30-day retention) whenever the file exists, independent of whether the scan passed — `if: always() && hashFiles('gitleaks.sarif') != ''`.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`, so bumping Go means editing `go.mod`.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes `${GITHUB_REF_NAME#v}` under dist-tag `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`. PRs never publish (`github.event_name == 'push'` gate). Authenticated with `NODE_AUTH_TOKEN: ${{ github.token }}` against `https://npm.pkg.github.com`, scope `@tactical-agent-neural-knowledge` — no external npm credential exists or is needed.
- `ci.yml` has `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true` — a second push to the same ref kills the first run, including a half-finished publish. `security.yml` has no concurrency group, so a weekly history scan and a same-minute push scan can run side by side.
