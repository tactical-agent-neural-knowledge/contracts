# Neurons · .github

refreshed 2026-10-08 · a887d51f4d82

- Two workflows now (was one): `ci.yml` (`check` + `publish-ts`) and the new `security.yml` (secret scan). Both declare `permissions: contents: read` at the top.
- CI calls `buf` directly from `bufbuild/buf-setup-action@v1`, never `make`. A change to the `Makefile` alone is therefore not exercised by CI — the two must be kept in step by hand.
- The breaking check is the point of `ci.yml`: `.github/workflows/ci.yml:31` says a wire break here "would be a production incident in web/mobile/agent-runner, so it is caught at the source". It runs only `if: github.event_name == 'pull_request'`.
- Trap, and the reason the step has three lines instead of one: `actions/checkout` leaves a PR on a detached merge commit with no local `main`, so the step must `git fetch --no-tags origin main:main` before `buf breaking --against ".git#branch=main"` can read it. The same applies locally on a fresh clone. `fetch-depth: 0` exists purely for this; shallowing it breaks the comparison, not the build.
- The staleness gate is `buf generate` followed by `git diff --exit-code --stat gen/`, failing with `::error::gen/ is stale. Run 'make gen' and commit the result.` Regenerating with a different buf or plugin version than the pins in `buf.gen.yaml` will trip it.
- `publish-ts` versions without committing (`npm version --no-git-tag-version`): a `v*` tag publishes `${GITHUB_REF_NAME#v}` under dist-tag `latest`, a push to main publishes `0.0.0-canary.${GITHUB_SHA::12}` under `canary`. Gated on `github.event_name == 'push'`, so PRs never publish; `needs: check` so a stale-gen or breaking failure blocks it too.
- `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress: true` on `ci.yml` — a second push to the same ref kills the first run, including a half-finished publish.
- `security.yml` is inlined rather than calling a reusable workflow, and the file's own header comment explains why: this repo is **public**, the org's shared `workflows` repo is **private**, and GitHub refuses a reusable workflow call from private to public *before any job is scheduled* — the failure mode was a nought-second run with no job and no log, which is how it silently stayed red on every push until someone looked. Any future reusable-workflow call from this repo will hit the same wall; inlining (and keeping the copy in sync by hand) is the deliberate workaround, not an oversight.
- `security.yml`'s gitleaks job is deliberately fail-closed: the scan step always `--exit-code 0`s (so a scanner crash can't masquerade as "no findings"), and a separate `report` step is what actually fails the job — it errors if `gitleaks.sarif` doesn't exist at all ("an unknown result is a failure, never a pass") and again if the finding count is nonzero. A false positive is silenced with a dated `.gitleaksignore` entry, never by touching this logic.
- `security.yml` scans the working tree (`gitleaks dir`, `fetch-depth: 1`) on every PR and push to main, and the full git history (`gitleaks git .`, `fetch-depth: 0`) only on the Monday 06:17 UTC cron — a credential committed and reverted is still a leak in a public repo, but the expensive full-history walk is weekly, not per-push.
- gitleaks is pinned to `8.30.1` and fetched as a release tarball (`VERSION` env var), not via a marketplace Action — the comment notes the Action asks for an org licence key, which this public repo doesn't have.
- `--redact` is load-bearing on both the log and the uploaded `gitleaks.sarif`: this repo is public, so an unredacted finding in a run log would leak the secret to everyone who can read the repo, which is everyone.
- The Go version is never written in `ci.yml`: `actions/setup-go@v5` takes `go-version-file: go.mod`, so bumping Go means editing `go.mod`. The TypeScript check is `npm install --no-audit --no-fund && npm run build` in `gen/ts` on node 24 — a tsc compile of the generated sources, no tests.

## Verified

`npx --yes @bufbuild/buf lint` and `npx --yes @bufbuild/buf breaking --against '.git#branch=main'` — the two `ci.yml` checks reproducible outside Actions; both passed. Neither workflow was executed; `security.yml`'s gitleaks step requires a network fetch of the release binary and was not run here.
