# Neurons · proto
refreshed 2026-10-14 · 65c4439b3e7d

- 27 packages now under `proto/tank/<domain>/v1/` (up from 22 at the last refresh): new since then are `board`, `books`, `canvas`, `remediation`, `security` — plus the pre-existing `agentctl` growing substantially. README.md's package table is stale and only documents 13 of the 27; don't trust it as the full list, read `find proto -name '*.proto'` instead.
- `agentctl.proto` is the single contract between the in-sandbox runner and agent-control (`RunnerService`/`ControlService`) — it imports `agent`, `blocks`, `board`, `books`, `canvas` and re-exposes their types as RPC payloads (`BooksSummaryRequest` wraps `tank.books.v1.*`, etc.), so it's the widest-blast-radius file to change: a field removed here breaks every tool the runner calls.
- `agentctl.RunContext` is the one message handed to a run at start: everything the sandbox knows about itself (ids, phase, policy, approved plan, repo access, attachments, `channel_purpose`/`channel_goal`, `task_class`) lives on it — read it before assuming a run needs a new side-channel RPC instead of a new field here.
- `agentctl.PolicySummary.tools_gate_destructive` (field 9) was added 2026-10-07 to fix a real incident: the control plane evaluated `policy.tools.gate.destructive_tool` patterns but never told the sandbox about them, so the gate the policy promised silently never opened. Any new policy enforcement that's supposed to run *inside* the sandbox must be mirrored onto `PolicySummary`, or it isn't enforced at all.
- `PolicySummary.mode` is `propose_only | can_merge` — the wire form of a Tread's `pull_requests` setting (`review` vs `merge_when_green`); `can_merge` is what lets a run merge its own PR without a human click.
- `security.proto` encodes one explicit rule as its data model: **controls are the primitive, frameworks (SOC 2, etc.) are views over them** — there is exactly one `Control` registry and a framework never introduces a second set of facts, only a `FrameworkClause` mapping onto existing controls.
- `security.ControlState` has no "assumed true" state: `NOT_YET` covers "probably true but unevidenced", and a check that hasn't run recently must report `UNKNOWN` rather than replay its last answer — a registry that flatters the system is treated as worse than no registry.
- `remediation.proto` is the seam between judging and fixing by design: the control registry (messaging core) decides what's wrong and cannot run anything; the remediation engine (agent control plane) holds the sandboxes/GitHub App and cannot change a control or framework mapping. A finding crosses this message boundary one way only — a system marking its own homework is treated as a non-system.
- `remediation` is propose-only by default (a PR a human merges); `AUTO_APPLY` is a narrow, explicitly enumerated exception. Every remediation must carry the regression test it requires, checked against the PR, not left as a suggestion.
- `board.proto` / `books.proto` / `canvas.proto` back the Neuralboards/Neuralbooks/Neuralcanvas tools exposed to runs via `agentctl` (`ListBoards`/`ReadBoard`/`DrawOnBoard`, `BooksSummary`/`BooksCreateInvoice`/`BooksRecordPayment`, `WriteUpThread`/`ReadCanvas`/`AskCanvas`) — these are product surfaces a run acts on, not internal plumbing.
- `blocks.proto` and `events.proto` and `realtime.proto` and `richtext.proto` declare messages only, no `service` — they're payload/event shapes consumed by other packages' RPCs (e.g. `blocks.PlanStep` inside `agentctl.ApprovedPlan`), not independently-called services.
