# Neurons · proto

refreshed 2026-10-10 · e52a377a71d9

- 27 domains now (5 new since the last refresh: `board`, `books`, `canvas`, `remediation`, `security`), one package each, always `proto/tank/<domain>/v1/<domain>.proto` with package `tank.<domain>.v1`. `CLAUDE.md`: "One proto package per domain, version suffix `v1`."
- `security.proto` is the control registry: one rule decides the whole file — "**Controls are the primitive; frameworks are views over them.**" A `Control` is a single fact with an owner, a `check_kind`/`check`, an `evidence_query` and a `ControlState` (MET, PARTLY, NOT_YET, NOT_APPLICABLE, plus the machinery states UNKNOWN/stale). A framework (SOC 2 today) is `FrameworkClause`s mapping onto existing controls, never a second set of facts — "If answering SOC 2 required writing down anything that is not already a Control, the model is wrong."
- `security.proto`'s honesty rule: a control nobody can evidence is `NOT_YET` even if everyone believes it holds, and a check that hasn't run recently reports `UNKNOWN` rather than repeating its last answer (`Control.stale`, `max_age_seconds`). A registry that flatters the system is worse than none, because every later phase (remediation) reads from it.
- `remediation.proto` is the deliberate seam between "the half that judges and the half that fixes": the control registry (messaging core, `security.proto`) can only `SubmitFinding` across this boundary and can't run anything; the remediation engine (agent control plane: GitHub App, sandboxes, gate engine) can't change a control or a framework mapping. The file's own comment: "A system that can mark its own homework is not a security system."
- `remediation.proto`'s four rules, load-bearing for anyone adding a `Class`: propose-only by default (`AUTO_APPLY` is narrow and the eligible class list is short and declared); every remediation carries the regression test it's held to, not a suggestion; a finding fans out to every repo/workspace the same `Class` applies to (fix the class, not the instance); every remediation names the run that drove it (the flight recorder).
- `board.proto` — Neuralboards: "an infinite board inside the workspace, shared by people and the agent," distinguished from every other canvas because a `Frame` (`ObjectKind.OBJECT_KIND_FRAME`) can hold the *running application*, not a picture of one. 10 object kinds including `STICKY` (the FigJam/Lucidspark note), `CONNECTOR` (joins two objects and follows them), and `DRAW` (freehand path).
- `canvas.proto` — Neuralcanvas: pages with per-`Block` revisions (`BlockKind`), a `Decision` ledger, nested tables/images/templates, and `Source` citing what a page was written from — `WriteFromThreadRequest`/`Ask` on `CanvasService` are the entry points agentctl wraps (`WriteUpThread`, `ReadCanvas`, `AskCanvas`).
- `books.proto` — Neuralbooks: "the money side of a small business, kept by an agent inside the workspace." Double-entry underneath; amounts are integer cents in the workspace currency; ids are Snowflake strings like everywhere else. `InvoiceStatus` has five terminal-ish states including `VOID` ("cancelled; never counted") — don't confuse it with `PAID`.
- `proto/tank/agentctl/v1/agentctl.proto` nearly tripled (372 → 1045 lines) and is now the full MCP-tool surface, not just run control: `BooksSummary`/`BooksCreateInvoice`/`BooksRecordExpense`/`BooksRecordPayment`/`BooksReport`, `ReadBoard`/`DrawOnBoard`/`ArrangeBoard`/`ListBoards`, `WriteUpThread`/`ReadCanvas`/`AskCanvas` all live here as the runner's calls into the control plane, wrapping the `books`/`board`/`canvas` services. It also gained `RefreshNeuralKnowledge` (the RPC that drives this very refresh), `OpenThread`, deployment registration (`RegisterDeployment`/`GetDeployment`), and settings RPCs (`SetChannelAgentSettings`, `SetWorkspaceAgentPolicy`, `SetChannelRepoAccess`) — still the runner ↔ control-plane-only contract, authenticated by the per-run `RUN_TOKEN`, never reachable from the messaging core.
- Product vocabulary never reaches the wire. `proto/tank/channel/v1/channel.proto:7`: a Channel "is presented as a 'Tread' in the product… The wire name stays Channel." A Radar is `CHANNEL_TYPE_MONITOR = 5`, implemented in `tank.monitor.v1`.
- Unread-count trap, and the two comments disagree: `Channel.last_seq` (channel.proto:44) still says "unread = last_seq - last_read_seq", while `ChannelReadState.unread_count` (channel.proto:77-85) documents why that arithmetic is wrong — thread replies and deleted messages also consume a `channel_seq`. Use `unread_count`; it is `optional` so a client can tell "server said zero" from an older server saying nothing.
- `optional` is used throughout as deliberate presence, not nullability: unchanged-field semantics in `UpdateChannelRequest`/`SetChannelPreferenceRequest`, "this replaces nothing" in `DecideBenchmarkRequest.supersedes_id` (topo.proto), the empty-vs-unconfigured distinction in `TopoPreferences.configured` (workspace.proto). Dropping `optional` to tidy a field silently changes meaning.
- `events.proto` grew six new envelope payloads for the two newest realtime surfaces: `CanvasBlockChanged`/`CanvasChanged`/`CanvasEditing` and `BoardObjectsChanged`/`BoardChanged`/`BoardPointer` (ephemeral presence ones on `typ.{ws}.*`, not stored). Same pattern as the rest of the file: one payload per fact, `google.protobuf.Any` in the envelope, subjects scoped `evt.{ws}.<domain>.{id}`.
- `realtime.proto` added `canvas_ids`/`board_ids` to the client's subscribe frame (subscribing is what makes another person's edit arrive — a client that never asks is unaffected) and two new ephemeral `ClientFrame` variants, `CanvasEditingFrame`/`BoardPointerFrame`, rate-limited like typing and never stored, mirroring `tank.events.v1.CanvasEditing`/`BoardPointer` on the server side.
- `admin.proto` gained `EndMemberSessions`: ends every session a member holds without touching their membership or any bot/API token — the admin's answer to "a laptop went missing," as opposed to `RemoveMember`, which only ends sessions as a side effect of taking the person's last membership. Returns `sessions_ended` so the caller can tell "it worked" from "there were none" (the common case, which otherwise reads as failure).
- Cross-package imports are real and make FILE-level breaking bite across domains: `topo` and `search` import `tank.message.v1`, `admin` imports `tank.workspace.v1`/`tank.channel.v1`, and now `events` imports `tank.board.v1`/`tank.canvas.v1`. A field removed from an imported file fails the breaking check in every file that merely references it.
- Adding a domain needs only a new `proto/tank/<domain>/v1/<domain>.proto` plus `make gen`: managed mode supplies `go_package` unless the file sets `option go_package` itself (four of the five newest domains do: books, canvas, remediation, security). Remember the TS barrel at `gen/ts/src/index.ts` is hand-written and still doesn't cover any of the five.
- Never renumber or reuse a field number, and never remove a field before every client has shipped without it (`CLAUDE.md`). `make breaking` / the PR's breaking check catches the first; nothing but discipline catches the second.
