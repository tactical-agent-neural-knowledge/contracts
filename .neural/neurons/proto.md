# Neurons · proto

refreshed 2026-10-08 · b57522e4f7aa

- 27 domains now (up from 22), one package each, always `proto/tank/<domain>/v1/<domain>.proto` with package `tank.<domain>.v1`. Five are new this cycle: `board`, `books`, `canvas`, `remediation`, `security`. `CLAUDE.md`: "One proto package per domain, version suffix `v1`."
- Product vocabulary never reaches the wire. `proto/tank/channel/v1/channel.proto:7`: a Channel "is presented as a 'Tread' in the product… The wire name stays Channel." Same discipline in the new files: Neuralboard → `board.v1`, Neuralbooks → `books.v1`, Neuralcanvas → `canvas.v1`.
- `board`, `books`, `canvas`, `remediation` and `security` are all self-contained: none of the five imports another `tank/*.proto` file (checked via `import "tank/`). Only `admin`, `agentctl`, `blocks`, `events`, `message`, `realtime`, `search`, `topo`, `workspace` have cross-package `tank/` imports. `agentctl.proto` is the one file that pulls in three of the new domains (`agent`, `blocks`, `board`, `books`, `canvas`) for its runner-facing request/response wrappers.
- `proto/tank/remediation/v1/remediation.proto` is a deliberate separation of powers, stated in its own header comment: the control registry (messaging core) judges and submits a `Finding` via `SubmitFinding`; the remediation engine (agent-control) is the only thing that can act on it and run code. `RemediationService` has no RPC that changes a control, retires a probe or marks a finding resolved — that asymmetry is the whole design, not an oversight to "complete" later.
- `remediation.proto`'s `Class.max_disposition` gates everything: `DISPOSITION_AUTO_APPLY` requires `reversible = true` and `gate_kind` set, and a class with `lockout_risk = true` can never be AUTO_APPLY regardless of what else it declares. `SubmitFindingRequest` is idempotent on `(finding_id, control_version)` — resubmitting marks the previous remediation `REMEDIATION_STATE_SUPERSEDED` rather than opening a second PR.
- `proto/tank/security/v1/security.proto`'s one rule, from its header: "Controls are the primitive; frameworks are views over them" — a `FrameworkClause` (e.g. SOC 2 "CC6.1") only ever maps onto an existing `Control`, never adds a new fact. `ControlState.CONTROL_STATE_UNKNOWN` is forced whenever a check is stale (`Evidence.stale` / `max_age_seconds` exceeded) rather than reporting the control's last known answer — a stale check must never read as green.
- `security.proto`'s `CheckKind.CHECK_KIND_NONE` means no check exists yet, and such a control can only ever be `NOT_YET` or `UNKNOWN` — never `MET`, because nothing is watching it. `ControlState.CONTROL_STATE_PARTLY` and `CONTROL_STATE_NOT_APPLICABLE` both require a non-empty `Control.reason`; that's convention only (not enforced by the schema), so a reviewer has to catch an empty one.
- `proto/tank/agentctl/v1/agentctl.proto` is 1043 lines across two services: `RunnerService` (sandbox → control plane, authenticated by per-run `RUN_TOKEN`, every id a Snowflake decimal string) and `ControlService` (platform/API → control plane). `RunnerService` is where the board/books/canvas RPCs the runner calls live (`BoardResearch`, `DrawOnBoard`, `BooksCreateInvoice`, `WriteUpThread`, `AskCanvas`, …); `RemediationService` and `SecurityService` are not wrapped here at all — they're called directly, cross-service.
- `StartRunRequest.mode` (agentctl.proto:707-713): `""` for an ordinary run, `"neural"` for a Neural Knowledge refresh — skips planning and works in `repo` regardless of what the Tread is bound to. `skip_neural_knowledge` exists purely to A/B the same task with and without the layer. `ControlService.RefreshNeuralKnowledge` is idempotent while a refresh is already active for a repository — this refresh's own invocation goes through that path.
- `PolicySummary.tools_gate_destructive` (agentctl.proto:61-69) was added 2026-10-07 after a real gap: the destructive-tool deny patterns existed in every workspace's policy and were evaluated by the control plane, but were never told to the sandbox — so the gate never opened and the command just ran. The comment on the field states this plainly: "A deny list the runner cannot see denies nothing." Any new policy field that's meant to constrain the runner must round-trip into `PolicySummary`, or it has the same silent gap.
- `proto/tank/agent/v1/agent.proto`'s `TreadSettings.pull_requests` (string: `"review"` default or `"merge_when_green"`) and `pr_reviewer_ids` control what happens after an agent opens a PR; `TreadDeployment` (on `RepoBinding.deployment`) is TANK's own hosting for a Tread's generated repo — `CreateTreadRepo` / `SetTreadDeployment` wake or sleep it on TANK's cluster.
- Unread-count trap, unchanged: `Channel.last_seq` (channel.proto:44) still says "unread = last_seq - last_read_seq", while `ChannelReadState.unread_count` (channel.proto:77-85) documents why that arithmetic is wrong. Use `unread_count`.
- `optional` is used throughout as deliberate presence, not nullability: `UpdateChannelRequest`, `DecideBenchmarkRequest.supersedes_id`, `TopoPreferences.configured`. Dropping `optional` to tidy a field silently changes meaning.
- Nine files carry an explicit `option go_package` despite managed mode (billing, catalog, monitor, platform, topo, books, canvas, remediation, security) — it must match the managed prefix exactly or `gen/go` lands in the wrong directory. `board.proto`, the newest domain, has none and relies on managed mode, so this isn't "every new domain declares it".
- Never renumber or reuse a field number, and never remove a field before every client has shipped without it (`CLAUDE.md`). `make breaking` / the PR's breaking check catches the first; nothing but discipline catches the second.
